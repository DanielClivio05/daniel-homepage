Project

Book Nook Lane

The system an independent bookstore runs on, live at booknooklane.com.

Inventory, sales, events, customer bookings, a shared photo library, and a bilingual public site in English and Italian — all of it operated by one person who is not technical and should never have to call me to change a sentence on the homepage.

The shop hasn't opened yet, so the tables are nearly empty. It's deployed and waiting rather than busy, which means the interesting part of this project is the design rather than the traffic.

How it's put together

Three decisions I'd defend

The public site can't write to anything

Row-level security is on for all seven tables. An anonymous visitor can read published events and published site content, and nothing else. Bookings don't get an insert policy — they go through a single SECURITY DEFINER function that carries a honeypot field, so the browser never holds a credential that can touch customer data. That collapses the attack surface to one function I can actually read in full and reason about.

The booking email fails open

When a booking lands, a Postgres webhook fires a Deno edge function that emails the shop through Resend. If Resend is down, the function fails without rolling anything back — the booking is already committed. Losing a notification is an annoyance; losing a customer's booking because a third-party email provider had a bad afternoon is not acceptable, and the two failure modes shouldn't be coupled.

The owner doesn't need me

The public site is bilingual in English and Italian, the photo library is shared, and site copy goes through a plain-language editor rather than a CMS with a learning curve. This was the actual requirement: a system whose usefulness doesn't decay the moment the person who built it is busy with finals.

What I'd do differently

I don't yet know which of my assumptions are wrong. Nothing here has met a real week of trading. I designed the schema around how I imagined the shop would work, and some of that will turn out to be wrong in ways no amount of thinking finds ahead of time. I'd rather say that than describe it as battle-tested.

The design assumes exactly one operator. There is one auth user and no concept of roles, a second staff member, or a second location. That was the right scope for the shop, and it's the kind of decision that's cheap now and expensive in two years, so I'd at least have left room for a users table.

The print assets live outside the application. The A4 QR posters and the opening-hours signage are generated by a Python script using ReportLab, run separately from the app. It works, but it means changing the opening hours in the admin doesn't change the sign on the door — two sources of truth for the same fact, which is the sort of thing that quietly goes stale.
